# R9 — How mature live-trading/betting frameworks decompose their production layer

Survey for the design of `dskit.production`. Eleven frameworks read from primary docs/source (URLs in §5). Domain-neutral throughout: "instrument" means whatever the decision is about, "venue" whatever executes it.

## 1. Per-framework findings

### 1.1 NautilusTrader
**Decomposition.** A `NautilusKernel` owns seven components: `MessageBus`, `Cache`, `DataEngine`, `ExecutionEngine`, `RiskEngine`, `Portfolio`, `Trader` (which manages user `Actor`s, `Strategy`s and `ExecAlgorithm`s), plus a `Clock`. Hexagonal "ports and adapters"; the core is single-threaded for "deterministic event ordering". `Strategy` = `Actor` + order management; actors have lifecycle states READY → RUNNING → STOPPED with DEGRADED/FAULTED/DISPOSED, and `on_start/on_stop/on_bar/on_order_filled/...` handlers, plus `on_save()/on_load(state)`.
**Flow.** Data: adapter → `DataEngine` → `Cache` → bus topic → `on_quote()`. Execution: `strategy.submit_order` → (`OrderEmulator` | `ExecAlgorithm` | `RiskEngine`) → `ExecutionEngine` → `ExecutionClient` → venue; events (`Accepted`, `Filled`, `OrderDenied` with a reason string) flow back through the cache to the strategy.
**Symmetry.** "Backtest, sandbox, and live systems share the `NautilusKernel`"; what swaps is the clock, the data/execution clients and the message flow (direct vs async channels). Even so: "live inputs and latency can still cause behavioral differences." The **sandbox** adapter is "a simulated execution client that uses the `OrderMatchingEngine` to simulate order execution against live market data" and takes the same matching flags as the backtest venue (`starting_balances`, `oms_type`, `account_type`, `book_type`, `fill_model`, `bar_execution`, `trade_execution`, `queue_position`, `reject_stop_orders`, ...).
**Guards.** `RiskEngine` is "a gateway between strategy orders and execution": instrument exists, price/qty precision and bounds, GTD expiry, `max_notional_per_order`, balance/margin, rate throttlers (`max_order_submit` default 100/s), and a `TradingState` of Active / Halted ("denies all new submit and modify") / Reducing (only position-reducing orders). `bypass` exists as an explicit flag.
**Persistence.** `Cache` with Redis/Postgres backing restores "general data, currencies, instruments, accounts, orders, and positions"; `CacheConfig` knobs `encoding`, `buffer_interval_ms`, `flush_on_start`, `persist_account_events`, `tick_capacity`/`bar_capacity`; `snapshot_orders`/`snapshot_positions` options; `load_cache=true` restores before clients connect. **Reconciliation** at startup consumes order-status → fill → position reports ("These reports represent external reality"); unknown venue orders become `EXTERNAL` orders; `generate_missing_orders=True` synthesises fills for position gaps; continuous checks via `inflight_check_interval_ms` (2000) / `inflight_check_threshold_ms` (5000), `open_check_interval_secs`, `position_check_interval_secs`; node timeouts `timeout_connection_secs` 60, `timeout_reconciliation_secs` 30, `delay_post_stop_secs` 10.
**Notifications.** None as a product; the bus can be externally backed.
**Weaknesses.** Heavy Rust/Cython build; rapid API churn (config classes and doc paths renamed between versions during this survey); one `LiveNode` per process; DB-backed cache refused on a host event loop.

### 1.2 QuantConnect LEAN
**Decomposition.** An `AlgorithmManager` loop drives a set of handlers selected by `Launcher/config.json` "environment": `setup-handler`, `result-handler`, `data-feed-handler`, `real-time-handler`, `transaction-handler`, `history-provider`. Backtesting = `BacktestingSetupHandler / BacktestingResultHandler / FileSystemDataFeed / BacktestingRealTimeHandler / BacktestingTransactionHandler`; live-alpaca = `BrokerageSetupHandler / LiveTradingResultHandler / LiveTradingDataFeed / LiveTradingRealTimeHandler / BrokerageTransactionHandler`. **live-paper keeps `BacktestingTransactionHandler`** with a `PaperBrokerage` — the simulated executor is literally the backtest object fed by the live feed. `ITransactionHandler` owns `Orders`, `OrderEvents`, `OrderTickets`, `Process(OrderRequest)`, `AddOpenOrder`. `BrokerageSetupHandler.Setup` connects, runs `Initialize()`, `LoadCashBalance`, `LoadExistingHoldingsAndOrders`.
**Decision seam.** Algorithm Framework: Universe → Alpha (`Insight`) → Portfolio Construction (`PortfolioTarget`) → Risk Management (`ManageRisk(targets)` returns *adjusted* targets; models chain sequentially) → Execution. Brokerage model = fee/fill/slippage/buying-power/settlement + `CanSubmitOrder/CanUpdateOrder/CanExecuteOrder`; "In live trading, LEAN doesn't ignore your `SetBrokerageModel`... uses some of the brokerage model rules to catch invalid orders before they reach your real brokerage."
**Loop.** Per time slice: set time, update securities, corporate actions, margin calls, scheduled events, `OnData`/`OnFrameworkData`, transaction synchronous events; live-mode branches exist inside the loop ("in live mode we always want to have our order match the order at the brokerage"). Handlers: `OnOrderEvent`, `OnBrokerageDisconnect/Reconnect/Message`, `OnMarginCall`, `OnWarmupFinished`, `OnCommand`, `OnEndOfDay/Algorithm`.
**Persistence.** `ObjectStore` key-value for state across deployments (with a documented stale-cache hazard); holdings retained on stop; results retained across redeploys.
**Notifications.** `Notify.Email/Sms/Telegram/Web/Ftp` — live only, cloud only.
**Symmetry doctrine.** The reconciliation page lists divergence causes: look-ahead in custom data, discrete time steps, tick-slice width (1 ms vs ≤70 ms), fills "take about half a second", no market impact, no borrow cost, whole-share rounding, **non-deterministic restarts**, **existing positions**, brokerage-model mismatch. Advice: scheduled events not exact-time conditions, ObjectStore for state, identical parameters, a separate account.
**Weaknesses.** Cloud-centric; `if live` inside the engine loop; "LEAN actively terminates live algorithms when it detects interference outside of the algorithm's control".

### 1.3 Backtrader
`Cerebro` gathers feeds, strategies, observers, analyzers, writers, sizers and a broker. The **Store model** (`IBStore.getdata()`, `IBStore.getbroker()`) is the live seam; "there is no real difference when it comes to use the backtesting module or the live data module." Live disables `runonce`/`preload`; `quicknotify` delivers broker notifications immediately. Data feeds emit status (`CONNECTED, DISCONNECTED, CONNBROKEN, NOTSUBSCRIBED, DELAYED, LIVE`) via `notify_data`; orders via `notify_order` (`Submitted, Accepted, Rejected, Partial, Completed, Expired`); `backfill_start`/`backfill_from` replay history first. No guard layer, no persistence, no notifications. Documented limits: "If there is an open position for an asset at the beginning of operations or orders given by other means change a position, the trades calculated in the Strategy in cerebro will not reflect the reality"; `tradeid` unsupported live; cash/value are "always the latest values received". Development is dormant (README still targets Python ≥ 3.2).

### 1.4 vn.py (VeighNa)
`MainEngine` + `EventEngine` (thread-safe queue, dedicated dispatch thread) + `BaseGateway` + function engines + apps. `BaseGateway` contract: "thread-safe... non-blocked... reconnect automatically", callbacks `on_tick/on_trade/on_order/on_position/on_account/on_contract/on_quote`, abstract `connect/close/subscribe/send_order/cancel_order/query_account/query_position`. `OmsEngine` caches ticks, orders, trades, positions, accounts, contracts, active orders. CTA app: `CtaTemplate` with class-level `parameters`/`variables`, hooks `on_init/on_start/on_stop/on_tick/on_bar/on_trade/on_order/on_stop_order`, trading verbs `buy/sell/short/cover`, `get_engine_type()` (backtest vs live), local stop-order simulation; `BacktestingEngine` runs the same template. Persistence = `cta_strategy_setting.json` + `cta_strategy_data.json` (`sync_data` after every trade). **Risk**: `RiskManagerApp` *monkey-patches* `main_engine.send_order`; rules `ActiveOrderRule, DailyLimitRule, DuplicateOrderRule, OrderSizeRule, OrderValidityRule` subclass `RuleTemplate`; settings in `risk_manager_setting.json`; a blocked order emits a log + `EVENT_RISK_NOTIFY`. Notifications: `EmailEngine` (SMTP queue thread). Weaknesses: mutable JSON files as the only state, monkey-patch interception, GUI-centric.

### 1.5 Freqtrade
**Loop** (every `internals.process_throttle_secs`, default 5): fetch open trades from persistence → pairlist → OHLCV → `bot_loop_start` → `populate_indicators/entry_trend/exit_trend` → update open orders (`check_entry_timeout`, `adjust_order_price`) → exits (stoploss/ROI/signal, `confirm_trade_exit`) → `adjust_trade_position` → entries (`custom_entry_price`, `leverage`, `custom_stake_amount`, `confirm_trade_entry`). Backtesting runs the same callbacks once per candle; "backtesting will **never** replace running a strategy in dry-run mode." `dry_run` (default `true`) uses identical logic, a `dry_run_wallet`, and a separate SQLite file.
**Guards.** Protections (`StoplossGuard`, `MaxDrawdown`, `LowProfitPairs`, `CooldownPeriod`) as JSON with `lookback_period_candles`, `trade_limit`, `stop_duration_candles`, `only_per_pair`, `only_per_side`, `unlock_at`; locks align to candle boundaries; pairlist filters chain. `max_open_trades`, `tradable_balance_ratio`/`available_capital`, `unfilledtimeout`, `order_types` incl. `emergency_exit`/`force_exit`, `stoploss_on_exchange` (+`_interval`, `emergency_exit: market` on failure), `initial_state` (`running|paused|stopped`), `force_entry_enable` off by default.
**Persistence.** SQLAlchemy `trades`, `orders` (`ft_trade_id`), `trade_custom_data` (`trade.set_custom_data`), pair locks; "never run any writing query while a bot is connected"; in-memory dicts "not persisted after a bot-restart" and deprecated.
**Notifications/control.** Telegram commands `/start /stop /pause /reload_config /forceexit /locks /unlock /show_config`; `notification_settings` per event `on|silent|off` over `status, warning, startup, entry, exit, entry_fill, exit_fill, entry_cancel, exit_cancel, protection_trigger, protection_trigger_global, strategy_msg`; webhook with `retries`, `retry_delay`, `timeout`, `form|json|raw`; producer/consumer publishes analyzed dataframes over websocket.
**FreqAI.** Retraining on a separate thread; `live_retrain_hours`, `expiration_hours` (refuse stale models), `identifier` (reuse a saved model), `purge_old_models`; models and `historic_predictions.pkl` on disk; backtest emulates retraining with a sliding window (`train_period_days`, `backtest_period_days`). `lookahead-analysis` "chains backtests and pokes at the strategy to provoke it to show lookahead bias."
**Weaknesses.** Candle cadence, single CCXT exchange, one trade per pair, layered config precedence (CLI > env > files > strategy).

### 1.6 Hummingbot
`Clock(ClockMode.REALTIME|BACKTEST, tick_size)` calls `c_tick` on every registered iterator; `run_til` sleeps, `backtest_til` advances deterministically. Connectors: `ConnectorBase`, `OrderBookTracker`, `UserStreamTracker`, `ClientOrderTracker`; `AsyncThrottler` with declared `RateLimit(limit_id, limit, time_interval, weight, linked_limits)` used as `async with throttler.execute_task(limit_id)`, FIFO, `safety_margin_pct`. **V2 strategies**: `StrategyV2Base` → `ExecutorOrchestrator` → typed `Executor`s; `Controller.control_task` = `update_processed_data()` then `determine_executor_actions()`; `ExecutorBase` (`start/stop/early_stop/control_task`, `validate_sufficient_balance`, `place_order` via `strategy.buy/sell`, `process_order_*_event`, `get_net_pnl_quote`, `executor_info` for persistence); `ControllerConfigBase` (`id`, `manual_kill_switch`, `total_amount_quote`) from YAML, re-read at `config_update_interval`. **Persistence**: `MarketsRecorder` → SQLite `Order`, `OrderStatus`, `TradeFill`, `FundingPayment`, `Executors`, `Controllers`, `Position`, `MarketState`; `restore_market_states` → `market.restore_tracking_states`. **Paper**: `PaperTradeExchange` wraps a real connector's order book, `set_balance`, fills market orders against depth, matches limits on crossing. Guards: `kill_switch_rate` ("At what profit/loss rate would you like the bot to stop?"), `balance_asset_limit`. Notifications: Telegram, MQTT bridge (commands + events). Weaknesses: V1 and V2 coexist; Cython; crypto-only.

### 1.7 Jesse
Strategy hooks `should_long/should_short/go_long/go_short/should_cancel_entry`, `update_position`, `before/after`, `on_open_position/on_close_position/on_increased_position/on_reduced_position/on_cancel`, `filters`, `watch_list`; attributes `self.position`, `self.orders`, `self.buy/sell/stop_loss/take_profit`, mode flags `is_backtesting/is_livetrading/is_papertrading`. Live/paper via an official plugin: "The package is pre-built and the access is limited to those with an active license." Notifications Telegram/Discord/Slack, custom via `self.log`. Weaknesses: closed-source live path; mode flags inside the strategy invite branching.

### 1.8 Zipline lineage (zipline-live → zipline-trader / zipline-broker; pylivetrader)
Broker classes (`IBBroker`, `ALPACABroker`) plug into `run_algorithm(..., state_filename=...)`; pylivetrader "saves the property fields to the disk that you add to the `context` object" (file or Redis) and warns that `initialize()` may run again on restart: "check if the fields are from the other session". `handle_data` fires each minute, `before_trading_start` at a fixed time. No guard layer, no reconciliation. Weaknesses: fork-of-fork lineage, pickled context, Python 3.6 pins.

### 1.9 flumine (Betfair)
**Decomposition.** `BaseFlumine` holds `streams`, `clients`, `markets`, `strategies`, a `handler_queue`, `trading_controls`, `client_controls`, `middleware`, logging controls and workers. `_process_market_books`: latency check → update `Market` → middleware ("executed in the order it is added and before the strategies are processed") → `strategy.check_market_book` → `process_market_book`; `_process_close_market`, `_process_cleared_orders`, `_process_end_flumine`. Strategy hooks: `add, start, process_new_market, process_market_catalogue, check_market_book, process_market_book, process_orders, process_closed_market, finish`; constructor limits `max_selection_exposure=100`, `max_order_exposure=10`, `max_trade_count`, `max_live_trade_count=1`, `multi_order_trades`; a `validate_order` hook; `RunnerContext` (`invested`, `trade_count`, `live_trade_count`, `executable_orders`).
**Controls.** "By default flumine will try to prevent coding errors which result in flash crashes." Default trading controls `OrderValidation`, `MarketValidation`, `StrategyExposure` (+ `ExecutionValidation`); client control `MaxTransactionCount` (5000/hour, hourly reset, cancels exempt). `BaseControl._validate` raises `NotImplementedError`; a failure calls `order.violation(msg)` → `OrderStatus.VIOLATION` ("order never placed due to failing controls"). `Order` keeps `status_log`, raw `responses`, `customer_order_ref`, an `info` dict.
**Clients/execution.** `BaseClient(paper_trade="simulated order placement using live data", order_stream, transaction_limit, capital_base, commission_base, min_bet_validation, best_price_execution, simulated_full_match, market_recording_mode, execution_cls)`; execution is `order_package.client.execution.handler(order_package)`. `FlumineSimulation` is a "Single threaded implementation of flumine for simulating strategies with betfair historic (or self recorded) streaming data", muxing streams by epoch, applying `simulated_latency` per order package; `SimulatedMiddleware` "Calculates matched amounts per runner" with per-strategy isolation to "Prevent double counting of passive liquidity". `LoggingControl` is a thread with a queue and `_process_{config,strategy,market,trade,order,balance,cleared_orders,closed_market,end_flumine}` hooks — persistence is bring-your-own via this seam.
**Weaknesses.** Venue price ladders live inside `OrderValidation` (domain leaks into the guard layer); exposure semantics are betting-specific; no built-in notifications.

### 1.10 Barter-rs
`Engine<Clock, State, ExecutionTxs, Strategy, Risk>`; `process(EngineEvent)` returns an `EngineAudit`; events `Shutdown`, `Command` (`SendCancelRequests`, `SendOpenRequests`, `ClosePositions`, `CancelOrders`), `TradingStateUpdate` (Enabled/Disabled → `OnTradingDisabled` strategy), `Account`, `Market`. Strategy is four traits (`AlgoStrategy`, `ClosePositionsStrategy`, `OnDisconnectStrategy`, `OnTradingDisabled`). `RiskManager::check(state, cancels, opens)` returns four iterators: approved cancels, approved opens, refused cancels, refused opens. "Use mock MarketStream or Execution components to enable back-testing on a near-identical trading system as live-trading." An `AuditStream` feeds an `EngineState` replica for "non-hot path monitoring"; trading can be toggled from an external process.

### 1.11 Lumibot
React-style lifecycle: `initialize`, `before_market_opens`, `before_starting_trading`, `on_trading_iteration` (loops until `minutes_before_closing`, sleeping `sleeptime` = `"30S"|"1H"|"1D"`), `before_market_closes`, `after_market_closes`, `on_abrupt_closing`, `on_bot_crash`, `trace_stats`, `on_new_order/on_partially_filled_order/on_filled_order/on_canceled_order`, `on_parameters_updated`. Broker and DataSource abstractions; "The same strategy lifecycle works from historical backtests to paper trading and live trading." Brokers include Polymarket — evidence that a calendar-gated iteration loop spans prediction markets as well as equities.

## 2. Cross-framework synthesis

| Framework | Decision↔execution seam | Swapped for backtest/paper | Guard layer | Persistence | Notify/control |
|---|---|---|---|---|---|
| Nautilus | `submit_order` → RiskEngine → ExecEngine → client | clock, data/exec clients; sandbox = live data + matching engine | RiskEngine: validation, notional, balance, rate, TradingState | Cache DB (Redis/PG), snapshots, `on_save/on_load`, reconciliation | bus only |
| LEAN | Insight → PortfolioTarget → ManageRisk → Execution → ITransactionHandler | handler set from config.json; live-paper reuses backtest tx handler | RiskManagement models (chain) + brokerage `CanSubmitOrder` | ObjectStore, holdings loaded from broker | Email/SMS/Telegram/Web (cloud) |
| Backtrader | Strategy → Broker (from Store) | Store gives live data+broker | none | none | none |
| vn.py | CtaTemplate → CtaEngine → MainEngine.send_order → Gateway | BacktestingEngine runs same template | RiskManager rules via patched send_order | JSON setting/data files | Email |
| Freqtrade | populate_* + callbacks → exchange (ccxt) | dry_run wallet, same loop; backtest per candle | protections, stoploss guards, timeouts, initial_state | SQLite trades/orders/custom_data | Telegram/webhook/Discord/API |
| Hummingbot | Controller → Executor → connector | ClockMode, PaperTradeExchange over live book | kill_switch_rate, balance limits, throttler | SQLite via MarketsRecorder, restore states | Telegram, MQTT |
| Jesse | should_*/go_* → plugin | mode flags; plugin paper | — | — | Telegram/Discord/Slack |
| zipline-live | context/handle_data → Broker | broker class | none | pickled context state file | none |
| flumine | process_market_book → market.place_order → controls → client.execution | SimulatedClient/paper_trade, SimulatedMiddleware | default-on controls, VIOLATION status | LoggingControl hooks (BYO) | none |
| Barter | AlgoStrategy → RiskManager → ExecutionClient | MockExchange/mock stream | RiskManager 4-way approve/refuse | AuditStream | external toggle |
| Lumibot | on_trading_iteration → Broker | Broker/DataSource | — | — | (BotSpot) |

**Consensus decomposition** (every mature system has all seven, under different names):
1. **Clock** — the only source of "now"; real or replayed (Nautilus, Hummingbot `ClockMode`, Barter `Clock`, LEAN real-time handler).
2. **Feed** — subscriptions + status (`DELAYED/LIVE/DISCONNECTED`) + backfill (Backtrader Store, Nautilus DataEngine, flumine Streams, vn.py Gateway).
3. **State cache / blotter** — orders, positions, balances, instruments, indexed and restorable (Nautilus Cache, vn.py OmsEngine, flumine Blotter, LEAN Portfolio/Transactions).
4. **Decision** — small hooks, no venue knowledge (`Strategy`/`Actor`/`Controller`/`CtaTemplate`/`on_trading_iteration`).
5. **Guard** — a chain between decision and execution that returns approved and *refused-with-reason* (Nautilus `OrderDenied`, flumine `VIOLATION`, Barter `RiskRefused`, LEAN `ManageRisk`), plus a global trading state (Active/Reducing/Halted; `initial_state`; kill switch).
6. **Executor** — abstract submit/cancel/modify + venue reports; simulated, paper (live data + simulated fills) and live implementations behind one interface; venue-specific validation belongs here (LEAN brokerage model).
7. **Recorder + control plane** — an append-only event sink (LEAN result handler, Hummingbot MarketsRecorder, flumine LoggingControl, Barter AuditStream) and external commands (start/pause/reduce/halt/liquidate/reload) with per-event notification routing.

**Consensus message flow.** feed event → cache → decision → *intent* (`OrderRequest` / `PortfolioTarget` / `OrderPackage`) → guard(approve | refuse+reason) → executor → venue events (`submitted, accepted, rejected, partial, filled, canceled, expired`) → cache → decision callbacks → recorder/notifier. Records kept everywhere: one per intent with a status log and raw venue responses; fills; position and balance snapshots; a per-cycle audit.

**Consensus on symmetry.** Keep the decision object byte-identical; swap exactly three things: clock, feed, executor. Three rungs — backtest (replayed feed + simulated executor), paper/sandbox/dry-run (live feed + the *same* simulated executor: LEAN live-paper, Nautilus sandbox, flumine `paper_trade`, Hummingbot paper, Freqtrade `dry_run`), live. Everyone concedes residual divergence and names its causes (LEAN's list; Nautilus "optimistic" queue fills; Freqtrade's backtesting assumptions) — so the frameworks that take it seriously ship *tests* for it (Freqtrade `lookahead-analysis`, LEAN OOS-backtest overlay) rather than promises.

## 3. Design implications for `dskit.production`

The owner's constraints map one-to-one onto the consensus; the recommended decomposition (names provisional, all tier-1 stdlib unless noted):

| Class | Responsibility | Hooks / interface |
|---|---|---|
| `Clock` (ABC) | sole source of time | `now()`, `wait_until(ts)`; `WallClock`, `ReplayClock(ticks)` |
| `Calendar` | gate ticks; supplied object, JSON-describable windows | `is_open(ts)`, `next_open(ts)`; exchange calendars as a tier-2 pack |
| `Feed` | fetch **through the onboarding connector seam**; report status and staleness | `fetch(asof) -> Observations`, `status` (`BACKFILL|LIVE|STALE|DISCONNECTED`) |
| `Decider` | load the training run's document + node objects (hash-verified), run the signal/capital nodes on live observations | `load(run_dir)`, `decide(observations, ledger) -> [Intent]`, `on_save()/on_load()` |
| `Intent` | domain-neutral decision record: key, direction or target, size, limit, tif, tag, reason, idempotency id | value object; serialises to JSON |
| `Guard` (ABC) | pre-execution check; chain; refusal carries a reason | `check(ledger, intents) -> (approved, refused)`; `@abstractmethod _check_one` |
| `TradingState` | ACTIVE / REDUCING / HALTED, settable by control plane and by guards | queried by the loop, never branched on in the decider |
| `Executor` (ABC) | the **object** the loop is handed; never learns a venue | `validate(intent)`, `submit(intent) -> Ack`, `cancel(id)`, `reports(since)`; `DryRunExecutor` (records, never fills), `SimulatedExecutor` (fills at observed price — the backtest's object), child-supplied live executors |
| `Ledger` | in-memory blotter rebuilt from records: open intents, fills, positions, balances | `apply(event)`, `snapshot()` |
| `Reconciler` | compare `Ledger` to `executor.reports()` at start and every N ticks; emit discrepancy records; policy object decides adopt/halt | `reconcile(ledger, reports) -> [Discrepancy]` |
| `TickRecord` | **one record per tick**: asof, wall time, calendar verdict, observation digest, intents, guard verdicts, acks, latency | append-only JSONL under a serve dir keyed by the training config hash |
| `Notifier` (ABC) | per-event routing `on|silent|off`, retries | `notify(event)`; `LogNotifier`, `WebhookNotifier` (urllib); Telegram etc. as packs |
| `ControlPlane` | external commands: start/pause/reduce/halt/liquidate/reload; `initial_state` | file- or RPC-sourced; every command is a record |
| `ServeLoop` | orchestration only: clock → calendar → feed → decider → guard → executor → ledger → record → notify | the *mode* is the triple of objects passed in — no `if mode ==` |

**"Actually move money" as a loud act.** Copy LEAN's `live-mode` + Freqtrade's `dry_run: true` default + Nautilus's explicit `bypass`: the live executor must be (a) a distinct class, (b) named in JSON under `execution.kind`, and (c) armed by a separate graded field (e.g. `"execution": {"kind": "...", "armed": true}`) whose absence yields `DryRunExecutor`; the first `TickRecord` and the startup notification state which executor is live.

**Copy.** LEAN's config-selected handler set (JSON names the Clock/Feed/Executor classes); Nautilus's refusal events with reason strings and its TradingState triad; flumine's default-on guards and `VIOLATION` as a terminal, recorded status with `status_log`; Freqtrade's protection schema (`lookback`, `trade_limit`, `stop_duration`, per-key vs global locks), `initial_state`, `unfilledtimeout`, per-event notification levels and webhook retry knobs; Hummingbot's declared rate limits and `kill_switch_rate`; Nautilus's reconciliation knobs (`reconciliation_lookback_mins`, `inflight_check_threshold_ms`, `open_check_interval_secs`, `generate_missing_orders`, node timeouts); FreqAI's `expiration_hours` → refuse to serve artifacts older than a configured age; pylivetrader's lesson → `on_load` must be idempotent and restarts must be assumed; Barter's per-event audit and four-way approve/refuse; LEAN's divergence list as a test checklist; Freqtrade's `lookahead-analysis` as the model for a parity test (replay the serve loop over the backtest window and diff decisions).

**Avoid.** Mode flags inside the decision object (Jesse `is_livetrading`, vn.py `get_engine_type`) and mode branches inside the loop (LEAN `AlgorithmManager`); monkey-patching to insert guards (vn.py); venue rules inside guards (flumine price ladders) — they belong to `Executor.validate`; pickled context as state (zipline); mutable JSON files as the only state (vn.py) — records are append-only, state is a fold over them; two parallel strategy frameworks (Hummingbot V1/V2); notifications that only work in one deployment (LEAN cloud-only).

**Config knob families** (`notes` on every object; only graded fields enter the identity hash): `clock`, `calendar`, `feed` (connector ref, cursor, `max_staleness`), `decider` (run dir, pinned artifact hash, `max_artifact_age`), `guards` (ordered list of `{kind, params}`: exposure, intent rate, duplicate window, cooldown, drawdown halt, staleness, trading-state), `execution` (`kind`, params, `armed`, `unfilled_timeout`, `emergency` action), `reconciliation` (lookback, inflight threshold, open-check interval, on-discrepancy policy), `records` (dir, snapshot interval, purge), `notifications` (channels, per-event level, retries), `control` (`initial_state`, command source), `loop` (`throttle_secs`, `max_ticks`, `stop_at`).

## 4. Pitfalls & anti-patterns
- **Restart amnesia**: state lost or `initialize()` re-run (pylivetrader, LEAN "non-deterministic restarts") → rebuild the ledger from records, then reconcile against the executor before the first decision.
- **In-flight orders at crash** → idempotency ids on every intent (flumine `customer_order_ref`, Nautilus client order id) and an in-flight check with a threshold.
- **Pre-existing positions** (Backtrader, LEAN) → reconcile and record them as `EXTERNAL`, never silently adopt.
- **Retries that double-submit** → retry only after a status query; count failed transactions (flumine `MaxTransactionCount` counts failures too).
- **Rate limits** → declare limits per executor (Hummingbot) and cap reconciliation queries per cycle (Nautilus `max_single_order_queries_per_cycle`).
- **Look-ahead and timing** → decide at candle/bar close plus a scheduled offset, not "at exact time" (LEAN); lock guards to bar boundaries (Freqtrade).
- **Optimistic simulation** (Nautilus queue fills, Freqtrade fill assumptions) → record the executor kind in every tick record so paper results are never confused with live.
- **Silent defaults** → default-deny params; a guard chain that is empty must be a loud config choice, not an omission.
- **Guard bypass as a code path** → if a bypass exists (Nautilus `bypass`), it is a graded config field and appears in the startup record.
- **Model/config drift between training and serving** → the decider loads the run's own document and hash-verified artifacts; a mismatch is a refusal, not a warning.
- **Clock drift and stale feeds** → `max_staleness` guard fed by `Feed.status`; halt, don't decide, on `STALE`.
- **Time zones and calendars** → a single UTC clock; calendar supplied as an object; holidays are data, not code.
